# Estimate Issue

给 Issue 草稿或已有 Issue 提供建议 Estimate。遵循仓库根目录 `a2a_dev_process.md` 的「Estimate 管理规则」；点数包含实现、测试、文档和验收，最终由 Owner 确认。本技能可在 Issue 创建前、AI Ready=No 时使用，评估不等于实施许可。仅授权 Ledger 自动创建的待分诊 QA Bug 按 [正文校验例外](../../../.github/issue-contract.md#自动待分诊-bug-的例外) 固定 TBD 并延后调用本技能；分诊后、实施前仍需调用及 Owner 确认，普通 CLI/API 创建不适用。

## 输入与证据

- 草稿：读取待提交的完整正文和用户提供的上下文；尚无 Issue 编号不妨碍评估。
- 已有 Issue：读取正文、全部评论及明确关联的规格、设计、API、ADR；识别已批准范围和最新决定。
- 读取根目录及受影响目录的 AGENTS.md、Issue 模板，查看相关实现、测试、配置和真实验证命令。用 `rg` 定位入口并沿关键调用关系检查，不能只依标题或文件数量估算。
- 可访问时查找同团队已完成、已验收且有确认点数的相似 Issue / PR；只读获取，不输出带凭据的 remote。历史查询范围以足够形成有效参照为限；无参照时明确采用起始尺度。历史仅供校准，不能覆盖当前需求。

区分已知事实、估算假设和缺失证据，为结论引用文件位置或 GitHub 链接。访问失败、目标代码尚未接入和需求缺失分别说明；不存在的实现或测试不得描述为已验证。

## 分析工作范围

先把每项 AC 映射到需要的交付与验证，列出足以影响规模的工作项，不实施代码。对下列维度分别给出工作量驱动因素及依据；不适用的维度说明原因：

| 维度       | 需要查明的问题                                                             |
| ---------- | -------------------------------------------------------------------------- |
| 实现与复用 | 已有能力可复用到什么程度？需要新增或修改哪些逻辑、状态和模块？             |
| 接口与数据 | 是否跨服务或平台？是否涉及 API 契约、数据迁移、兼容、权限及回滚？          |
| 验证与验收 | 主流程和异常路径如何验证？已有测试设施能否复用？需要哪些环境、设备或数据？ |
| 文档与交接 | 是否需要规格、设计状态、API、ADR、运行手册或交接产物？                     |
| 依赖与协调 | 哪些依赖已明确？本 Issue 需要承担哪些集成、沟通或验证工作？                |
| 不确定性   | 未知项是否会改变范围、实现路线或验收方式？补齐它需要什么证据？             |

Feature、Bug、Design、Tech Debt 使用相同尺度：Bug 同时考虑定位和回归验证，不能依严重程度或代码修复行数判点；Design 包含状态设计与交接验收；Tech Debt 包含兼容和迁移验证。外部等待时长不计作工作规模，但依赖不明确可能导致 TBD。Risk、优先级、业务价值、Agent 速度与 token 成本不直接映射点数。

## 选择唯一结果

1. 先判断能否可靠估算：缺失信息若足以改变关键范围、实现路线或验证工作，选择 TBD，并列出解除条件。一般实现细节不必全部确定；能合理限定影响时可以给具体点数，同时披露假设。
2. 用流程中的五档参考及有效历史参照，对整体交付规模判断最匹配的一档。复杂度、覆盖面和必要工作共同决定点数；不把各维度机械相加，不使用小时到点数的公式，也不把 AC 或文件数量当作分数。
3. 解释为何符合所选档位，以及为何相邻档位不合适。若合理假设下仍跨越多个档位且无法收敛，选择 TBD；明确范围下处于相邻档位之间，可依据主导工作及验证负担选一档并说明。
4. 明显超过 8 点时返回 TBD，提出可独立验收的拆分建议；不将大型任务强行封顶为 8。父子 Issue 不重复累计，只有汇总用途的父 Issue说明这一点。
5. 复核已有估算时，先区分开工前建议与开工后范围变化。开工后的原点数保留，调整建议及原因另列，供 Owner 按流程记录；不能凭实际耗时重新改分。

完成条件：所有 AC 均有工作与验证映射，影响规模的未知项已披露，给出唯一合法 Estimate、可复核理由及下一步。缺少证据时以 TBD 完成评估，不虚构确定性。

## 输出与提交衔接

默认输出以下结构；Estimate 行只能含一个合法值，后续部分承载分析：

```text
Estimate: <1 / 2 / 3 / 5 / 8 / TBD 中的一个值>
状态：建议值，待 Owner 确认 / 已有 Owner 确认依据（附来源）
工作与验证：逐项 AC → 交付、验证、证据；补充必要的共用工作
规模判断：各适用维度的主要驱动因素；历史参照或起始尺度；相邻档位比较
不确定性：事实、假设、缺失信息及其影响
下一步：Owner 确认；或 TBD 的澄清问题、所需证据 / 拆分建议
```

用户或调用者明确只需要字段值时，最终仅输出 `1`、`2`、`3`、`5`、`8` 或 `TBD`，将分析保留给调用者可复核的工作记录。JSON 调用约定可用 `estimate` 字符串字段，但不能同时给出多个候选值代替结论。

提交 Issue 的调用者将结果写入正文唯一的 `### Estimate` 下，字段内容仅为值；分析依据放在已授权的 `[AI-PLAN]` 评论草稿或 Scope 下四级标题 `#### Estimate analysis`，不创建额外三级字段。Owner 未确认建议点数或结果为 TBD 时，保持 AI Ready=No。评估完成后仍按原有 Issue 模板检查完整契约。

调用者创建或更新 Issue 正文时，将完整最终正文保存到文件，使用 `node .github/scripts/issue-submit.cjs create --title <标题> --body-file <正文文件>` 或 `edit --issue <编号> --body-file <正文文件>`；可指定 `--repo OWNER/REPO`。统一入口对同一份正文执行 submission 校验并仅在成功后写入，禁止另用直接 gh/API 正文写入；只更新 Estimate 也须提供完整正文。校验失败时修正可确定的格式/枚举，缺失需求/Owner/环境保留未知，不伪造数据。机器校验、自动检查及可信 Ledger 例外见仓库根 `.github/issue-contract.md`；实施前另用 `issue-contract.cjs <正文文件> execution` 并核对批准证据。

技能本身只读分析，不创建或修改 GitHub Issue、不发表评论、不实施、不设置 AI Ready。用户已授权提交 Issue 时，由调用者执行提交并保留估算依据；技能不扩大该授权。其他 Agent 不支持技能发现时，可由调用者直接读取本文件并按相同流程执行。
