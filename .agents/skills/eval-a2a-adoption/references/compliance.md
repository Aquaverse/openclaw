# 分级合规核查

本清单区分 Issue 格式与优秀级处理过程。每项记 pass/fail/unknown/na，附规则来源、事实、证据；na 说明适用性。读取失败是 unknown；完整查询确认必需记录不存在才可 fail。

## 合格与良好：仅 Issue 格式

按当前模板及 Forms 检查最新 50 个非 PR Issue，每个对象的格式结果由以下适用项归并：任一 fail → fail；无 fail 而有 unknown → unknown；全部通过 → pass。

| ID         | 格式要求                                                                                                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-FIELDS   | 共用和类型专属必填字段非空，无 `_No response_` 或未填模板占位符。Feature 用户流；Bug 复现/预期实际/环境/严重程度；Design 用户流/平台/组件/状态/handoff；Tech Debt 技术证据/兼容回滚。明确允许 N/A/None 的字段须说明适用性。 |
| F-HEADINGS | 字段标题唯一、独占三级行，名称与 Form label 相同；字段内子标题四级或更深。                                                                                                                                                  |
| F-VALUES   | Type/Risk/Estimate/AI Ready/Severity 等枚举合法；Owner 格式合法。No/TBD 待分诊合法；Yes/TBD 若违反机器契约则为字段值组合不合法，仍属格式问题。                                                                              |
| F-AC       | AC-1 等编号唯一、非空，有明确验收表述；代码块或注释示例不当作 AC 定义。                                                                                                                                                     |

可用仓库共享 Issue submission 校验器辅助。仅当规范明确授权时，采用自动 Ledger 待分诊 Bug 的字段格式例外，并保存依据。

格式检查不验证 Owner 是否已确认点数、首次实施时序、行为需求是否批准、关联 PR、CI、Review、QA、人工审批或业务验收。需要这些证据的是优秀级流程核查，不将其失败混入 Issue 格式结果。普通开发工作仍受原仓库实施门槛约束。

选样完整且满 50 个时：至少 40 pass 为合格条件通过；至少 11 fail 为未通过；其余组合 unknown。40 pass + 10 unknown 仍达到要求；39 pass + 10 fail + 1 unknown 尚不能判不合格。完整分页确认仓库非 PR Issue 总数少于 50 个时直接不合格，即使全部格式合规；总数或分页未确认时记 unknown，不把截断采集当作数量不足。

## 优秀级：文件与处理过程

依 [file-integrity.md](file-integrity.md) 递归核验根流程及必需支撑文件；五个可选文件按明确规则排除。missing 阻止优秀，unknown 阻止宣称优秀；均不取消已满足的合格或良好。

对最新 10 个 PR 及其关联 Issue 核查：

| ID         | 要求与证据                                                                                                                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E-READY    | 实施前 AI Ready=Yes，Owner 确认具体 Estimate，需求/依赖澄清；有可定位的确认与时间。当前 Yes 不证明历史开工前已就绪。                                                                                                              |
| E-CHANGE   | 行为决策、范围变化和原点数保留在 GitHub；未决问题没有被继续实施，相关规格已同步。无需六类评论前缀全部出现。                                                                                                                       |
| E-PR       | PR 模板齐全，正常实现恰好一个主 Issue，AC 逐项映射；规格/文档/风险回滚和监督者有依据。关闭关键字使用 Closes 或 PR Contract 定义的合法别名；草稿允许明确标记未完成证据；可信 Quality Ledger 例外须符合当前分类规则及简短正文契约。 |
| E-EVIDENCE | 测试命令、退出码、日志/截图与正确提交关联；Review 独立检查最终 head diff，安全有结论或 N/A 理由；不能仅凭勾选框/自述判通过。                                                                                                      |
| E-GATE     | 已合并 PR 的适用 build/lint/types/unit/integration/Review/Merge gate 成功，人工审批及讨论解决、顺序正确；未合并的未来检查 na，失败或 pending 不等同已绕过门禁。                                                                   |
| E-QA       | 合并后 QA 针对实际合并 SHA，逐项 AC 验证并有业务验收；QA fail 需有分诊/修复依据，不能仅因发现缺陷就断言绕过合并门禁。                                                                                                             |

Review 绑定合并前最终 head，QA 绑定实际 merge/squash/rebase 结果，两阶段不能互替。按变更适用性核查 UI/设备/异常状态、API/迁移、Agent eval 等证据，不要求文档 PR 提供无关 UI 截图。

优秀级流程结果：归属已确认的适用项任一确证 fail → fail；无 fail 但有必需项 unknown、未完整读取证据、样本不足 10 → unknown；全部通过且满 10 个 → pass。关联对象不替换不合规样本，权限不足或 artifact 过期不能当作已证实违规。

可见外部交流只能检查已回写的决策，披露观测范围；本技能不重新执行全部产品 QA。优秀级失败仅限制优秀；合格/良好由 Issue 格式及各自周指标决定。
