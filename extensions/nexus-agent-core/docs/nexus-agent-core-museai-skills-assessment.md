# 第一部分：总结

## 一句话结论

Muse 快照里的旅行与预订技能文字**值得作为设计参考**，尤其是"订之前怎么核对、订完怎么确认、出了偏差怎么退回去重新规划"这几块，可以启发 Nexus 的 Booking 和 Journey 技能；但**财务（Moneywise）几乎没有可参考的内容**，基本要自己设计。

同时要分清两件事：**"Muse 的思路很匹配"不等于"现在的 Nexus 已经能做"**。例如 Nexus 目前的决策只能用来授权一个已准备好的动作，还不能承载"在 A、B 两个方案里选一个"这类行程选择；研究结果也还不能自动变成可追溯的证据。这些是技能文字补不上的，需要先补能力。

## 这是什么

- `MuseAI-Skills` 是第三方的一份**部分文件系统快照**，附带 Muse / Hatch 产品的技能文字和文档。它的 README 明确说：这既不是完整源码仓库，也不是可一键部署的包，来源和产品说法**没有被独立核实**，不代表官方发布，也不是经过验证的开源发布，其中"可用"不等于"可自由再授权"。
- 其中与旅行预订相关的技能有 7 个：行程规划、预订总入口、找地点，以及机票、餐厅订位、活动票、航班状态四个具体服务。另有约 100 条评测场景（见第二部分第 8 节，场景存在不代表曾运行或通过）。
- 我们的表格把三个子代理拆成 **35 个技能设计子任务**：Journey（行程）13 个、Booking（预订）10 个、Moneywise（省钱和账单）12 个。35 行是**能力设计任务，不等于要产出 35 个技能文件**。

## 怎么使用它

由于许可没有确认，本项目**只借鉴概念和做法，并独立重写**，不拷贝、不整体改写它的文字。技能目录里会留一份来源说明（参考了哪类思路，文本为自行撰写）；对外发布前需要先确认许可。

## 评估看四件事，不只是"能借多少"

| 维度              | 问的是什么                                             |
| ----------------- | ------------------------------------------------------ |
| 设计匹配度        | Muse 的设计思路和我们的任务对不对得上                  |
| 实现可移植性      | 抛开 Muse 专有的卡片、连接器、电话工具后，还剩多少能用 |
| 当前 Nexus 就绪度 | 以现在 Nexus 的工具和账本，能不能把它做出来、验证出来  |
| 许可与来源状态    | 借鉴的内容许可是否已确认；没有对应内容的就是原创       |

| ------ | ------------------------------------------ | ---- |
| 高     | 结构、字段、规则的思路和我们的任务高度吻合 | 6    |
| 中到高 | 大部分思路吻合                             | 1    |
| 中     | 只有一部分思路能借，其余要补               | 11   |

按子代理看：

- **Booking（预订）最好借**：10 个里设计匹配度高的有 4 个，当前能交付的切片也最多（就绪 2、部分 6）。重点是"选哪条渠道去订""下单前再核对一遍""防止重复预订""价格或条件变了就退回去，不要悄悄换"。但目前只有假供应商，真实预订至少要完成会话级锁定（G4a / T6）、真实 provider（G4b）、非 execution 材料的证据路径（G2），以及供应商答复与预订结果契约（G9）。
- **Journey（行程）其次**：13 个里高 2、中到高 1、中 6。重点是"统一的行程和待办清单""方案比较""把候选交给预订并规定返回什么"。多人协调、出差政策、旅行后收尾 Muse 里没有。**"让用户在几个方案里做选择"这一块现在没有承载它的决策类型，需要先设计。**
- **Moneywise（财务）要从头设计**：12 个里只有 2 个中、2 个低、8 个无；当前可交付的切片只有 M5、M6 两项的规则部分，Nexus 一侧还缺统一的财务记录和对账模型（G5a）、数据入口（G5b）。

## 为什么能参考，又不能照搬

- **能参考**：Muse 在"不能擅自决定、不能擅自花钱、办成要有证据"上和我们的方向一致，比如提交前给用户看完整条款、出现确认号才算订成、结果不明时先查再重试。
- **不能照搬**：除了许可没有确认，Muse 的技能依赖它自己的运行环境（专用机票卡片、选项卡片、电话工具、专有连接器和钱包），OpenClaw 里没有这些。
- **Nexus 已经替它做了一部分**：任务、审批、证据、回检在 Nexus 里是现成的，技能可以写得更短。

## 建议怎么做

1. **先补能力缺口再谈完成**：最关键的是"行程选择类决策"契约（G1）、"工具输出作为证据"的持久化捕获（G2）、约束与行程的结构化载体（G3）、财务模型（G5a）和供应商答复与预订结果契约（G9）。这些各自需要单独设计，**不能由技能文本顺带决定**；技能写完不等于这些能力有了。
2. **第一阶段做一条用假供应商跑通的纵向切片**，而不是先写设计匹配度最高的技能：最小的需求收集 → 交接给预订 → 供应商答复分类（此阶段只做模型评测）→ 预订前核验 → 用假供应商完成授权与执行 → 异常退回。
3. **Moneywise 单独立项**：先冻结统一的财务记录和对账模型、定数据入口，再写技能。
4. **评测**：从 Muse 的场景里挑选能保留的不变量，改写成 Nexus 的测试（第二部分第 8 节有迁移矩阵），其余场景分别标为"本轮不采用"或"延期评估"（8.3 节）。

## 需要你拍板的事

- 三个子代理是做成 OpenClaw 里三个独立代理，各自配一组技能，还是先放在同一个代理里？
- 技能放在 Nexus 插件里（推荐，只在插件启用时出现），还是放在 OpenClaw 仓库根的通用技能目录？
- 是否接受第二部分第 6.2、6.3 节的"目标包结构"与"触发所有权"（3 个主入口技能 + 2 个独立技能，其余做成参考文件）？
- G1 / G2 / G3 / G5a / G5b / G9 各自的 owner 与设计时间是否进入本轮开发范围？
- 真实供应商什么时候接？目前 Nexus 只有假供应商，设计文档要求接真实 R2 / R3 前先做完会话级锁定（G4a / T6）；这只是接入 provider 的前置，完整真实预订还需要 G4b、G2、G9。
- 行程选择类决策（J7）当前阶段只做到"授权已准备的动作"，一般行程选择是否另立设计？（建议另立，即 G1，见 5.5 节。）

## 主要风险

- **许可与来源未确认**：快照 README 称其来源未独立核实，且"可用不等于可自由再授权"。在确认前只能借鉴概念并独立重写，不能写"直接复用"。
- 缺口契约被技能文本顺带定义：G1 / G2 / G3 / G5a / G5b / G9 会产生新的持久契约，必须单独设计。
- 技能只是"指导文字"，不能保证模型一定照做。真正的约束仍然靠 Nexus 的服务端（审批、授权、账本）。
- Moneywise 要读银行和账单数据，隐私和授权要求最高，需要单独评审。

## 2. Muse 技能的关键设计

### 2.1 两种工作模式与职责分工

`travel-planning` 先判断当前请求处于哪个模式：**快速预订**（条目、日期、人数、范围已具体，直接走 Booking）或**行程规划**（仍有实质选择要做）。规划技能负责行程结构、研究、可行性和跨轮责任清单；Booking 负责实时库存、确切商业条款和交易。"看价格或库存"不等于"要订"，用户说过"先把计划做完"就要在后续有界请求里保持。

### 2.2 行程姿态

每个多段行程内部保持一个姿态：`planning only`（只规划）或 `ready to book`（可以订）。多段行程默认只规划；只有用户明确要开始预订、或明确要求交易才切换。只规划时，Booking 可以搜索、比较、核实条款，但不准备结账、不要乘客或支付信息、不以预订号召结尾。

### 2.3 三种状态分开

- 决定状态：proposed / selected / rejected。只有用户或其事先的委托能改变。
- 运行证据：unchecked / estimated / verified（含来源与取得时间）。
- 供应商状态：not applicable / not checked / found / available / requested / held / waitlisted / confirmed / unknown / failed / cancelled。

选中不等于可订，核实过的营业时间不等于实时库存。未核实的组件只能叫 selected 或 tentative，不能叫 locked in、secured、confirmed。

### 2.4 规划到预订的交接

`booking-handoff.md` 定义交给 Booking 的候选字段（姿态、已选项、地点、日期时间、人数、航段、单票 / 自转 / 换机场界限、弹性范围、预算与行李座位等需求、规划来源与取得时间），并把实时结果分类为：

- 精确匹配：行程签名一致，再比较新的商业条款；
- 在已授权弹性内；
- 实质不符：路线、时间、舱位、票务结构、价格或条件超出界限，退回用户；
- 该渠道未找到：不等于现实中不可订。

匹配行程不等于匹配票价；实时结果缺少精确匹配所需的事实时，算未核实，不能用规划来源补。

### 2.5 责任清单与规范行程

`operational-itinerary.md`：每个未完成事项记录 结果、负责人（planning / booking / 直接供应商 / 用户）、状态（investigating … completed / dropped）、下一步、证据状态、实质期限；已确认订单视为锁定；修改用"移动 / 替换 / 删除 / 撤销"四种操作加变更历史，撤销只恢复规划状态，不撤销真实预订；跨日用 `+1` 标记。

### 2.6 预订与提交边界

- 渠道优先级（`booking`）：连接的原生供应商，其次已连接的预订平台，已登录的供应商网站浏览器，市场或聚合站，电话，最后才交给用户。一条路不通就直接试下一条，不用问用户；不静默替换日期、机场、房型、价格。
- 提交前紧凑的最终核对：项目、日期时间、人数、变体、分项费用、总价、现在付与以后付、抵扣、支付来源（只给安全标签）、取消 / 退款 / 改签 / 未到场条款。
- 提交后只有出现确认页、确认号、票据或明确的已订状态才算成功；结果不明时不重复提交，先查已登录账户、再窄搜确认邮件，确认没订成才重试。
- 回执固定格式：状态（已确认 / 已保留 / 候补 / 受阻）、确认号、时间与地点、总额、下一个期限。

### 2.6.1 授权与付款语义（`payments-and-purchases.md`）

每次购买都要重新批准，绑定具体商家、金额和支付方式；批准不可预先授予、批量或自动化；待批准的结账约十分钟过期；浏览权限与支出批准是两套机制。

### 2.7 其他值得记的规则

- 偏好证据：明说的是偏好；跨可比预订重复出现的是暂定偏好；单次旧订单只是搜索线索；不从历史推断过敏、无障碍需求或愿意接受的非退款价格。
- 敏感信息（姓名、生日、护照、会员号、支付）只在提交时按供应商字段使用，不进普通记忆、笔记或文件。
- 监测只是轮询：只能承诺"每 30 分钟查一次"，不能说"发生那一刻就通知你"；检查结果要以运行记录为准。
- 电话：先备齐通话说明，通话方看不到聊天，不能暗示"我打过"，工具确认后才能报告已拨出。

**当前 Nexus 的限制（影响技能写法）**

- 只有假供应商（`fake_vendor_message` R1、`fake_booking` R2、`fake_payment` R3），没有真实库存或订单；技能不得声称有真实可订项。
- T6 会话级锁定未实现：在此之前不得宣称 R2 / R3 的真实执行有强授权保证；接入真实 provider 必须同时实现锁定并在安装版验证。
- 聊天里的核心审批卡片没有二次确认（见 `extensions/nexus-agent-core/docs/nexus-agent-core-control-ui-followups-1016.md` 末尾）；偏好确认没有聊天按钮。
- `tool_output` 证据引用未实现：研究结果、网页抓取、工具输出不能自动成为可取回原始字节的证据。
- **relation verifier 目前只理解 `predicate="executed"`**，其他谓词一律 unclassified；**fake provider 只返回 confirmation、toolName 和固定 note**，模式只有 ok / reject / drop_after_success / drop_before_send。所以供应商答复（已确认 / 条件满足 / 无库存 / 预付条款等）当前**不能进账本分类**，也没有对应 fixture（G9）。
- 技能提示词与 Nexus 已注入的协议并存：协议（`prompt.ts`）每轮常驻，技能按需加载，所以技能不要重复硬规则，只补领域判断。

## 5. 逐项评估

### 5.4 J2 偏好证据：允许转换与禁止转换

Muse 的三档（明说 / 重复出现 / 单次旧订单）与 Nexus 的三种 origin（stated / observed / task_exception）**不是一一对应**：task_exception 是对**当前 Task** 的临时覆盖，不是一档"历史证据"。技能必须按下表转换：

| 输入                                                        | 允许的转换                                                                                                                                       | 禁止的转换                                                                              |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 用户明确表达偏好                                            | agent 调 `nexus_preference_confirm`，用户在 Nexus 页面批准后成为 `stated`（agent 不能直接写 stated）                                             | 在用户批准前当作已确认的偏好使用                                                        |
| 多次可比较行为（跨多个可比较订单重复出现）                  | 写 `observed`：必须带 0 < confidence ≤ 1 与 sourceNote（说明从哪几个 Task 推出）；它只是候选，不参与任何自动路径；要升为 stated 必须再走 confirm | 自动成为授权；省略置信度或来源；不带 sourceNote                                         |
| 单次历史订单                                                | 只作为本次搜索 / 排序的线索，不落库                                                                                                              | 写成 observed、stated 或 task_exception；据此推断过敏、无障碍需求或愿意接受的非退款价格 |
| 用户或 agent 为当前 Task 明确登记的一次性覆盖（"这次例外"） | 写 `task_exception`：必须带 taskId，不带 confidence                                                                                              | 从单次历史订单自动推出一条 task_exception；把 task_exception 外推成 observed 或 stated  |
| 偏好的适用范围（目的地、同行人、起点与终点的区分）          | 按范围限定后再写                                                                                                                                 | 把一个城市的偏好迁移到另一个城市，或抽象成泛化的口味偏好                                |

### 5.5 J7 与 J9：不能由一个技能补齐的两项

**J7 decision-handoff**

Excel 要求的决策交接包含：当前事实、A / B 选项、影响、付款人、费用边界、截止时间、required_decider。而当前 `nexus_decision_request` 的参数只有 taskId、effect（kind 可省略，服务端据风险档推导）、actionIds，决策类型是授权类（`issue_action_grant`、`issue_standing_grant`）和 `acknowledge`，偏好确认另走 `nexus_preference_confirm`。它是**对已准备 action 的授权决策**，无法持久保存选项、影响、截止时间、决定人。

结论：拆成两部分，不把"选择方案"塞进授权决策，否则"选择方案"和"授权执行"会再次混在一起。

- **J7a（当前阶段可交付）**：只覆盖"对已准备 action 的授权决策交接"——怎么在 `nexus_action_prepare` 之后向用户解释这个动作、什么时候调用 `nexus_decision_request`、被拒后怎么回到规划。**明确不覆盖一般行程选择**。
- **J7b（前置缺口 G1）**：设计独立的 planning-choice 决策契约，能持久保存事实、选项、影响、付款人、费用边界、截止时间和 required_decider，决定可追溯，并与授权决策分开建模。在 G1 完成前，一般行程选择只在对话里进行，结果最多记为事项备注，**不当作决策、不当作授权**。

**J9 travel-research**

Excel 期望研究结果（浏览器、goplaces、weather）可以作为带来源与时间的证据。当前 `tool_output` 引用未实现，真实可用的证据路径只有 execution 自动登记和操作员上传 blob 后挂到 claim。所以拆成：

- **J9a（当前可交付）**：研究结果供模型使用并如实标注来源与取得时间；需要作为正式证据时，由操作员上传材料，再挂到 claim。技能不得声称"研究结果已自动成为证据"。
- **J9b（后续前置 G2）**：实现带 `runId / sessionKey / toolCallId` 的持久化 tool-output capture。
- **J9b 完成标准**：重启后仍能取回原始字节、来源和采集时间，并由 verifier 判定 relation（支持或反证）。

## 6. 落地方式

### 6.1 技能放在哪里

- **推荐放在 Nexus 插件内**：`extensions/nexus-agent-core/skills/<名字>/SKILL.md`，并在 `openclaw.plugin.json` 加 `"skills": ["./skills"]`。acpx、browser、canvas、diffs 等插件都这样做；构建脚本会把 `skills/**` 自动打进 npm 包，内置版 pkg 中 canvas 的技能也确实在包里。技能只在插件启用后出现，不改 OpenClaw 仓库根目录的 `src/` 或 `ui/`。
- 备选：放仓库根的 `skills/`（OpenClaw 通用技能）。不推荐，因为内容和 Nexus 工具绑定。
- 落地时需验证：插件技能目录在内置版与 npm 包两条路径下都能被加载。

### 6.2 目标包结构（提议，待你确认）

35 行是能力设计任务，**不是 35 个顶层 `SKILL.md`**。一行一个技能会带来触发描述重叠、上下文膨胀和规则重复。提议的结构：

- **每个子代理一个主入口技能**：`journey`、`booking`、`moneywise`。主入口只写触发条件、总流程和各模块的路由。
- **J1–J13、B1–B10、M1–M12 的多数作为主入口引用的参考文件**（`references/*.md`），按需读取；表 B 的"目标 artifact"列已逐项标出文件。
- **只有同时满足"可独立触发、有完整工作流、有独立验收标准、且不只服务某一个主入口"的才单独成为 `SKILL.md`**：目前提议两个——`subscription-management`（M9）、`telecom-bill-analysis`（M11）。
- **电话核实（B8）只服务 Booking，做成 `booking/references/phone.md`**，不做独立顶层技能，也不拥有预订状态。
- **授权、证据、完成门禁等硬规则继续由 Nexus 协议（`prompt.ts`）拥有**，不复制到每个技能；技能只补领域判断。
- 这样顶层 `SKILL.md` 共 5 个（3 个主入口 + 2 个独立技能）；35 项里 2 项独立成技能，其余 33 项落在参考文件里。

### 6.3 触发所有权

"可以独立触发"还不足以避免两个技能同时竞争，所以每类请求只有**唯一入口**，其他技能写明排除条件：

| ---------------------------------------------------------------- | ------------------------- | ------------------------------------------------ | ----------------------------------------------------------- |

| 范围已具体的预订意图（快速预订）、联系供应商、预订执行、改签取消 | `booking`                 | `booking-handoff`（与 journey 共用）、`phone.md` | `journey` 遇到范围已具体的预订意图时转交，不自行询价或预订  |

### 6.4 三个子代理怎么分

- OpenClaw 支持 `agents.entries.<id>.skills` 按代理限定技能集合；非空列表就是该代理最终可用的全部技能，空列表表示不暴露任何技能，省略则继承 `agents.defaults.skills`。
- 做法一：三个代理各配一个主入口技能（加各自的独立技能）；做法二：先一个代理加全部技能，之后再拆。"Agent Profile""Tools Surface"两类子任务决定做法，本文不评估。
- 注意：按代理限定技能不能阻止有 shell 能力的代理访问全局配置的 MCP 服务（OpenClaw 发布说明中有相关安全审计提示）。

### 6.5 技能写法原则

- 一个技能只写领域判断和行为规则；Nexus 工具的硬规则仍在 `prompt.ts` 里，不重复。
- 工具名用 Nexus 的 `nexus_*`；不引用 Muse 的运行环境工具。
- 如实写明限制：目前只有假供应商，不能声称有真实库存或订单；不能声称研究结果已自动成为证据；不把行程选择当作授权决策；不把供应商答复分类说成已进账本。
- **技能文本不得顺带定义 G1 / G2 / G3 / G5a / G5b / G9 的契约**（见 7.1）。需要在 P1 里借用事项 entities 等现有自由结构时，必须标注"权宜，非契约"。
- 入口技能和独立技能各配验收（见表 B 的验收类型和第 8 节）；技能文件和清单加简单测试（存在、命名、清单声明）。

### 8.4 评测原则

- 每条保留场景必须能写出"可观察的预期结果"，并能由 Nexus 自己的账本、工具调用序列或确定性断言判分，不能只靠模型自述。
- Nexus 一侧已有的行为测试（决策、幂等、完成门禁、unknown 对账）可继续用，不必靠模型判断。
- 需要新 fixture 或前置缺口的场景，在缺口关闭前一律标"受阻"或"待 G9 / G3"，不计入通过率。
- 有 live 需求的场景，真实供应商未接入前同样不计入通过率。
