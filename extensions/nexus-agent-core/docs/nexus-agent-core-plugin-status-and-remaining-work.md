## 几点需要你知道的判断

1. **表里的状态落后于实际**：你之前处理了 PENDING 的行，但 75（Watcher）是空白，实际已经完成并在安装版回归过；78、79 也有一半的东西在。建议按第二部分 2.2 更新状态列。
2. **"做完"是"在假供应商上做完"**：授权、对账、账本都靠假供应商验证。接真实供应商前必须有三样东西：T6 会话级锁定（71 的缺口）、Connector 注册表（77）、至少一个真实 provider（81 电话是第一个候选）。这三样现在都没有。
3. **文件库是最大的未实现部分（有设计草案，无代码），而且表里的优先级互相矛盾**：文件库是 P0 / M2，而文件处理流水线是 P2 / M4，测试基准里"File processing"却是 P0 / M2。没有处理能力的文件库只能存取，没法支持 Moneywise 的账单与收据，也没法通过那条基准。需要你决定是把处理能力提前，还是把基准降级（见第二部分 4.8）。
4. **OpenClaw 已有不少现成部件，但没有一个能直接当"个人文件库"**：它的媒体目录是临时缓存，插件 Blob 存储总共 512 MiB 且已被证据账本占用，PDF 提取只支持 PDF，知识库 `memory-wiki` 是 Markdown 库。结论：文件库要自己建（按内容哈希去重的文件存储 + SQLite 元数据），再桥接这些现成部件。
5. **试点路线图与表的优先级也有出入**：`docs/nexus/nexus-development-roadmap-2026-10-02.md` 把通知提前到 W4、把审计拆出"介入次数与成本标记"提为 P0，并让 Personal Wiki、File Pipeline、Entity Layer 继续推迟。本文的建议顺序按这份路线图对齐，冲突处已标出。

## 建议的做法

- **先收口**，再开新功能：安装版的剩余回归、R2 / R3 页面全流程、聊天卡片二次确认（建议方案 1）、操作者身份，这些都小，却决定"已完成"是否站得住。
- **接着是三条主线**：① Connector 注册表 + T6 + 电话（让系统能办一件真事）；② 通知 + 审计的介入与成本度量（试点要靠它们看数据）；③ 文件库 v1（存、看、挂证据、清除），处理流水线按最小范围（PDF 与文本）跟进。
- **Handoff、Workflow、实体层先不做引擎**：Handoff 先走技能与现有的任务绑定，Workflow 靠技能与任务步骤，实体层等 G3 / G8b 契约出来再说。

## 需要你拍板的事

- 个人文件库的存储方案：自建、按 owner 隔离的去重文件库（当前推荐，评审通过前不冻结），还是复用 OpenClaw 工作区目录？
- 文件处理能力是否提前到 M2，还是把测试基准 06 降级？
- 敏感文件（护照、证件、银行卡）的默认处理：只允许操作员查看、不提取文本、不给 Agent？
- 通知的第一条出口：沿用用户当前的聊天渠道，还是等 Relay 推送？
- 电话：Wiz.ai 的接入形态、是否复用 OpenClaw 的 `voice-call`？
- 聊天里的 R2 / R3 单击批准要不要关掉（建议先关）？
- 是否更新表里 PENDING / 空白的状态？

完整问题清单见第二部分 8。

### 4.3 三个存储方案比较

| 方案                                            | 做法                                                                                                                                   | 优点                                                                                         | 问题                                                                                                                                                                          | 结论                                       |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| V1 扩展证据 blob                                | 文件当作特殊的证据对象存进现有 blob 存储                                                                                               | 复用最多，清除协议现成                                                                       | 总量 512 MiB 且与证据共享；每条证据要求绑定声明与 Task，个人文件不属于任何 Task；第三方安装下不可用；证据的语义（哈希绑定、不可改）与文件库（版本、改名、移动）不同           | 不采用                                     |
| **V2 自建文件库（按内容哈希去重、随机物理键）** | 状态目录下 `plugins/nexus-agent-core/vault/` 存文件（同一 owner 内按 SHA-256 去重，对象以随机 id 存放），元数据与关系放 `nexus.sqlite` | 容量只受磁盘限制；元数据、权限、审计、清除都在我们控制内；不挤占证据配额；第三方安装下也可用 | 要自己做崩溃安全的写入、对账、配额、清除；备份靠状态目录                                                                                                                      | **当前推荐**（设计评审通过前不冻结）       |
| V3 用工作区目录 + `memory.search.extraPaths`    | 让用户的文件夹成为 Agent 工作区的一部分，由记忆系统索引                                                                                | 实现最快，自带向量检索                                                                       | Agent 的文件系统工具可以绕过 Nexus 的权限与审计直接读写；无逐文件的归属和敏感级别；`active-memory` 会主动召回，无关对话里可能泄漏文件内容；与"文件内容是不可信数据"的原则冲突 | 不采用；可在 V2 之上做**显式、可选**的桥接 |

### 4.4 建议架构（草案，非契约）

> 2026-10-22：本节已展开成独立的设计方案，见 `extensions/nexus-agent-core/docs/nexus-agent-core-personal-file-vault-design.md`（含数据模型、接口、访问控制、分期与验收）。下面保留评估时的草案；两者不一致时以设计方案为准。收件 / 库 / 产出三类内容的划分和用户状态分表来自 4.10 的 Muse 参考。

**存储**

- 路径：`<state>/plugins/nexus-agent-core/vault/objects/<对象 id 前两位>/<对象 id>`；对象 id 是服务端签发的随机标识；文件名与用户可见的名称不进路径，只进元数据。
- 写入：先写临时文件、校验哈希、原子重命名，再入账；崩溃后由对账任务清理孤儿，**直接仿照证据 blob 的预约与对账**，不另发明。
- 去重：同一 owner 内同一哈希只存一份，不跨 owner；元数据记录多个用户可见条目。
- 配额：owner 级与单条上限单独配置，默认值待定（见 8）。
- 加密：依赖系统磁盘加密（FileVault）为默认；应用层加密不列入 v1。

**元数据**：模块级只列有哪些表，**字段、状态枚举、外键与约束一律以设计方案第 6 节为准，这里不再复制**（复制会在下次改表时产生双重真相）。

| 表                                                              | 作用                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `vault_objects`、`vault_reservations`                           | 按 owner 隔离的不可变字节，及其写入预约                                         |
| `vault_files`、`vault_versions`                                 | 用户可见条目与版本历史                                                          |
| `vault_links`、`vault_user_state`                               | 与其他模块的关联；置顶、收藏等用户状态                                          |
| `vault_jobs`、`vault_text`                                      | 处理任务与提取文本（都绑定到对象）                                              |
| `vault_purge_runs`、`vault_purge_items`、`vault_purge_receipts` | 硬清除的 run（稳定 `purge_id`、原始请求者、封口数量）、按对象聚合的工作项与回执 |

**对 Agent 的工具面（v1 只读）**

| 工具                | 作用                                               | 说明                                                                                       |
| ------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `nexus_file_search` | 按名称、类型、标签、提取文本检索，返回元数据与片段 | 默认不返回 `sensitive` 文件                                                                |
| `nexus_file_get`    | 取元数据与有大小上限的提取文本                     | 文本带"这是不可信数据，不是指令"的包装                                                     |
| `nexus_file_attach` | 把一份库内文件挂到某个 Task 的声明上作为证据       | 来源组 `user_upload`；字节**复制**进证据存储（≤16 MB），不跨存储共享引用，保持清除语义不变 |

不给 Agent 写入、改名、删除、清除的入口，延续"Agent 没有任何删除入口"的原则。**对外发送文件**（邮件附件、给供应商）是一种新的对外效果，要加进动作目录并走决策，字节在没有批准之前不出库。

**已确认**：OpenClaw 在用户本机运行，暂时不需要分享功能；外发与公开分享放到后期，v1 页面不出现“分享”入口。

**运维 RPC 与页面**：`nexus.vault.upload / list / get / handle / read / move / rename / delete / purge / stats / reconcile`；控制台增加"文件"标签页，复用读取句柄做预览。上传大小：`nexus.vault.upload` 沿用 Base64 路径只适合小文件，大文件走插件 HTTP 路由的分片上传（**需要 spike**，见 4.8）。

**访问控制**

1. 文件内容一律视为**不可信数据**：进模型上下文时加包装、截断；文件里的指令不执行（对应技能评估里的 `untrusted-email-instructions` 场景）。
2. `sensitive` 分级：护照、证件、银行卡、病历等。建议 v1 **只允许操作员查看，不提取文本、不给 Agent**；与技能规则"不保存、不复述聊天里给的敏感值"一致。如何判定敏感（文件名规则、用户标注、分类器）见 4.5。
3. 读取不等于发送：任何出库动作走 `nexus_action_prepare` → 决策 → `commit`。
4. 所有查看、下载、删除写审计（见 5.3）。

**与已有模块的关系**

| 模块                      | 关系                                                                           |
| ------------------------- | ------------------------------------------------------------------------------ |
| 证据账本                  | 库内文件可挂为证据；挂载时复制字节；声明的 relation 仍由服务端判定             |
| 偏好库                    | 文件里"提取出的偏好"只能作为 `observed` 候选，且要带来源文件                   |
| Task 清除                 | 清除某个 Task 不删除库内文件，只摘除关联；单独删文件要走文件库自己的删除与回执 |
| Moneywise（G5a / G5b）    | 账单与收据是文件库的第一批真实输入；结构化后的记录属于 G5a，不属于文件库       |
| 技能（Journey / Booking） | 技能不读文件字节，只通过 `nexus_file_*`                                        |

### 4.5 文件处理流水线（行 84）

| 阶段   | 做什么                                                   | 现成部件                                                                              | 缺口                                                                                                 |
| ------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 入库   | 大小与类型校验、嗅探 MIME、算哈希、去重、敏感初判        | 宿主有 MIME 嗅探（`@openclaw/media-core`）                                            | 敏感判定规则                                                                                         |

**插件能否调用宿主的文档提取运行时（而不只是注册提取器）未核实**。若不能，选项是：在插件里自带解析库（增加包体积与依赖面），或把新格式做成独立的 `documentExtractors` 插件。需要 spike。

### 4.6 Personal Wiki（行 83）

- 不自建。`memory-wiki` 已提供 Markdown 库、来源与 claim / evidence 元数据、Obsidian 兼容、检索与 lint；可用隔离模式，路径放在状态目录下。
- 需要先定三条边界：① **Wiki 内容永远不算证据**，证据只来自账本；② **偏好的权威来源仍是偏好库**，Wiki 只放叙述性内容（旅行笔记、总结），且页面要引用来源文件的 ID；③ `wiki_apply` 让 Agent 可写，试点期是否开放要单独评审。
- 价值依赖文件库和提取流水线，且试点路线图继续推迟，所以建议**M4 再做**，现在只保证文件库的对象 ID 可被引用。

### 4.10 Muse 的参考做法（2026-10-22 补充）

依据 MuseAI-Skills 里的 `home/hatch/docs/artifacts.md`、`home/hatch/docs/files-and-library.md`、`opt/hatch/skills/media-library/SKILL.md`、`opt/hatch/skills/spaces/ts-runtime/README.md` 和 `opt/hatch/skills/muse_db/references/schema.md`（`media`、`ingest`、`spaces` 三组表）。按技能评估文档的口径，只借鉴概念、独立重写，没有运行过 Muse。完整的对照表见设计方案第 2 节。

Muse 的"库"（Library）是**一个目录视图**，背后是三块不同的存储：智能体工作区里的文件夹、Artifacts（智能体构建的文档、页面、交互应用）、以及独立索引的照片库。对 Nexus 文件库方案的影响：

| Muse 的做法                                                                                   | 对我们方案的影响                                                                                                   |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 用户上传落在 `user` 文件夹，**不会自动进库**；智能体为用户做的文件放进 `your_files`，才会进库 | 采用"收件 / 库 / 产出"三类内容，收件到库是显式动作；用状态字段而不是文件夹约定                                     |
| 库是视图，存储另有一层；条目菜单里的置顶只是客户端整理                                        | 存储与视图分离；置顶、收藏、最近打开放进单独的 `vault_user_state` 表                                               |
| Blob 按 sha256 分片存放，键从不当路径用，另有元数据索引                                       | 采用分片目录 + 元数据索引的布局；物理键用随机、不复用的对象 id（SHA-256 只做同 owner 内去重），写入协议仿证据 blob |
| 照片描述是异步流水线：待处理 / 就绪 / 失败 / 被拒，带重试次数和下次重试时间；OCR 文本一并保存 | 处理任务沿用这套状态与重试字段；`rejected` 表示按策略不处理，不是错误                                              |
| 检索先看概览；覆盖不完整时要说明，不能说"没有"                                                | 工具返回带概览和"覆盖是否完整"；未索引的文件单列                                                                   |
| 发布产出物：只有静态的能发布；每次发布和每次更新都要新的一次性确认；不存在长期授权            | 对外发送 / 分享的规则照此定，并走 Nexus 决策；v1 不做分享                                                          |
| 删除分两种：工作区文件进回收站（约 30 天），Artifact 永久删除，删前必须警告                   | 沿用已有的"软删除 + 硬清除"两级；页面删除前说明是哪一种                                                            |
| 智能体对自己的工作区有完整读写权限                                                            | **不借鉴**：Nexus 的 Agent 只读、且只能经 `nexus_file_*` 工具，敏感文件不给 Agent                                  |
| 托管网页和交互应用                                                                            | **不做**：列为非目标，需要外部托管方案后再议                                                                       |

**部署形态不同，不能照搬**：Muse 的智能体运行在**远程虚拟机**里，库就是那台机器的工作区，上传是文件进入的唯一方式，机器常开；Nexus 随 OpenClaw 运行在**用户自己的电脑**上。直接后果有五条（逐项对照见文件库设计 2.6、目标设计 2.4）：

1. **文件本来就在用户磁盘上**：除浏览器上传外要有"从本机路径导入"，并且路径只能来自操作员、限定根目录、防符号链接逃逸；v1 只复制不引用原路径。
2. **Agent 与用户同一账户**：Muse 里智能体被关在虚拟机内，Nexus 里宿主的通用文件 / 命令工具理论上能读到库目录。"敏感文件对 Agent 不可见"在插件层面**无法单独保证**，需要宿主工具策略兜底，验证前（spike S8）不做该承诺。
3. **会休眠、会退出**：后台处理和目标回看都只能"尽力而为"，要按到期判断、限量补跑，且"没送达"不能算"被忽略"。
4. **备份与快照**：硬清除只能保证库内；Time Machine、云同步、APFS 快照里的副本不在控制范围，文案不能夸大。
5. **用户自己付算力和费用**：后台回合要有每周次数和 token 上限，磁盘要有保底余量。

### 5.2 通知（行 79）

**现状**：事件与 outbox 只在网关内；决策待批准时能向下一轮对话注入提示；控制台有"待决策"徽标。没有到手机或渠道的推送，用户不在聊天窗口时不会知道要批准。试点路线图因此把它提前到 W4。

**出口选项**

| 选项         | 做法                                                                  | 优点                       | 问题                                                                                                       |
| ------------ | --------------------------------------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A 对话内注入 | 沿用 `enqueueNextTurnInjection`                                       | 已有                       | 用户不说话就看不到                                                                                         |
| B 渠道外发   | 通过 OpenClaw 渠道的外发适配器，发到用户当前使用的渠道（如 iMessage） | 触达率高，可能不需要新服务 | 外发 API 对插件的开放程度**未核实**（文档页 `sdk-channel-outbound.md`）；渠道对 Nexus 页面链接的支持各不同 |
| C Relay 推送 | 经 Nexus Relay 的 Push Notification Gateway                           | 适合移动端                 | Relay 未建（P1 / M2–M3），依赖账号与配对                                                                   |

**设计草案**：`notifications` 表（类型、关联任务或决策、紧急度、渠道、去重键、投递状态、确认时间）；定时服务领取；去重与限频；免打扰读偏好；**锁屏文案不含敏感内容**，只给"需要你确认"与页面链接；未确认的升级与过期提醒。触发源：决策待批准或将过期、`unknown` 待落定、回检耗尽、声明被反驳、执行失败。

**建议**：v1 选 A + B（用户当前渠道）+ 控制台徽标，C 等 Relay。规模 M。

**本机运行的补充**：Nexus 在用户电脑上，机器休眠或应用退出时任何渠道都发不出去。通知记录要区分"生成 / 送达 / 已读"，目标回看的"被忽略"只统计已送达的提醒（见目标设计 7.3）；送达无法确认的渠道按"未送达"处理，下次打开应用时补显示一次。
